RECOMENDACIONES SENIOR PARA HARDENING Y CONTINUIDAD
PROYECTO TCDX ISO SAAS
=====================================================

Fecha de preparación: 2026-04-30
Objetivo del documento:
Entregar a Codex una pauta completa, ordenada y accionable para trabajar sobre el repositorio
baruj77/tcdx-iso-saas sin romper la línea actual del proyecto.

Contexto general:
El proyecto TCDX ISO SaaS está compuesto por:

- Base de datos PostgreSQL en VM db.tcdx.int
- Backend Node.js / Express en VM bk.tcdx.int
- Frontend Next.js en VM www.tcdx.int
- AI Engine FastAPI en VM ai.tcdx.int

La arquitectura objetivo para producción real será privada:
- Backend, AI Engine y BD NO tendrán exposición directa a internet.
- Solo el frontend debería acceder a los servicios backend.
- Backend, AI Engine y BD deben quedar protegidos por red privada, firewall/security groups y secretos fuera del repositorio.
- El backend se reinicia con systemd: sudo systemctl restart tecdex-backend
- El AI Engine se reinicia con systemd: sudo systemctl restart ai-engine
- El frontend normalmente se compila y levanta con npm start desde /home/tecdex/frontend.

Regla principal:
No hacer cambios a ciegas.
Antes de modificar archivos, revisar estado actual, mantener compatibilidad con la demo funcional y evitar romper rutas, RBAC, multi-tenant, KPI, evidencias, auditorías, reportes, prefacturación y AI Engine.

1. PRIORIDAD MÁXIMA: ESTANDARIZAR SECRETOS BACKEND / AI ENGINE
=====================================================

Problema detectado:
El AI Engine usa token interno desde variables AI_INTERNAL_TOKEN o AI_TOKEN.
El backend, para llamar al AI Engine, busca el secreto en:
- OWN_AI_SHARED_SECRET
- AI_INTERNAL_TOKEN
- AI_TOKEN

Pero en la VM backend el servicio systemd tecdex-backend.service actualmente solo muestra:
Environment=NODE_ENV=production

No tiene EnvironmentFile configurado. Esto puede hacer que el backend lea secretos desde /home/tecdex/backend/.env, mientras el AI Engine lee desde /etc/tecdex/ai-engine.env.

Riesgo:
- Mismatch entre token backend y token AI Engine.
- Errores Unauthorized AI internal token.
- Configuración no reproducible si se reconstruye una VM.
- Secretos dispersos.

Recomendación:
Estandarizar configuración segura fuera del repositorio:

Backend:
  /etc/tecdex/backend.env
  OWN_AI_SHARED_SECRET=<mismo_token_real>
  DB_HOST=db.tcdx.int
  DB_PORT=5432
  DB_NAME=tecdex_saas
  DB_USER=<usuario_db>
  DB_PASSWORD=<password_db>
  JWT_SECRET=<jwt_secret>
  PORT=3000
  NODE_ENV=production

AI Engine:
  /etc/tecdex/ai-engine.env
  AI_INTERNAL_TOKEN=<mismo_token_real>
  DB_HOST=db.tcdx.int
  DB_PORT=5432
  DB_NAME=tecdex_saas
  DB_USER=<usuario_db>
  DB_PASSWORD=<password_db>
  BACKEND_API_URL=http://bk.tcdx.int:3000
  FRONTEND_URL=https://181.212.166.187:8443
  APP_ENV=production

Tareas para Codex:
1. Proponer override systemd para backend:
   sudo systemctl edit tecdex-backend

   Contenido esperado:
   [Service]
   EnvironmentFile=/etc/tecdex/backend.env

2. Mantener AI Engine con:
   [Service]
   EnvironmentFile=/etc/tecdex/ai-engine.env

3. Documentar que los secretos NO van al repo.
4. Agregar documentación en docs/OPERACION_SECRETOS.md o similar.
5. Crear script de validación sin imprimir secretos:
   scripts/check-secrets-runtime.sh

Criterios de aceptación:
- Backend y AI Engine usan archivos /etc/tecdex/*.env.
- El mismo token se usa en backend y AI Engine.
- Ningún secreto queda en GitHub.
- El script muestra solo largos LEN=xx, no valores reales.
- AI Engine responde correctamente endpoints protegidos con x-ai-token.

function serverError(res, error, publicMessage = 'Error procesando solicitud') {
  const isProd = process.env.NODE_ENV === 'production';

  return res.status(500).json({
    ok: false,
    error: publicMessage,
    ...(isProd ? {} : { detail: error?.message || String(error) }),
  });
}

module.exports = { serverError };

4. PRIORIDAD ALTA: DEFINIR POLÍTICA DE AUTOAPROBACIÓN DE EVIDENCIAS IA
=====================================================

Problema detectado:
El discurso funcional deseado es:
"La IA sugiere, anticipa y razona, pero no aprueba decisiones críticas sin humano".

Sin embargo, el código actual tiene lógica que puede autoaprobar evidencias si supera umbral, por ejemplo AI_AUTO_APPROVAL_THRESHOLD = 80.

Riesgo:
- Contradicción con enfoque auditor humano.
- Riesgo de auditoría real.
- Puede cerrar evidencias sin validación formal.
- Puede afectar salud ISO, KPIs o ciclo de vida de manera prematura.

Recomendación:
Cambiar autoaprobación por recomendación o preaprobación.

Opciones:

Opción A:
Mantener status = pendiente, y guardar:
metadata.ai_recommendation = "approve"
metadata.ai_acceptance_pct = 92
metadata.human_approval_required = true

Opción B:
Crear estado intermedio:
- pendiente
- recomendada_por_ia
- aprobada
- rechazada

No aprobar automáticamente salvo que el usuario defina explícitamente que lo quiere para demo.

Tareas:
1. Revisar backend/src/routes/evidences.routes.js.
2. Revisar frontend/src/app/evidencias/page.tsx.
3. Reemplazar mensajes de "aprobación automática" por "recomendación IA".
4. Mantener trazabilidad de score y razones IA.
5. No afectar evidencias ya aprobadas manualmente.
6. Recalcular salud ISO solo cuando haya aprobación humana o evento formal.

Criterios de aceptación:
- Ninguna evidencia cambia a aprobada solo por IA.
- La UI muestra recomendación IA y botón de aprobación manual.
- Queda claro que requiere revisión humana.
- Se mantiene el valor comercial del auditor IA.

7. PRIORIDAD MEDIA: CORS
=====================================================

Contexto:
Se detectó en backend/src/app.js:
app.use(cors());

Esto permite CORS abierto.

Ajuste según arquitectura real:
Para producción real, backend, AI Engine y BD estarán en red privada, no expuestos a internet.
Solo frontend debería acceder a backend.
Por lo tanto, CORS abierto baja de prioridad crítica a prioridad media.

Aun así, se recomienda restringirlo preventivamente, especialmente si algún día se publica el backend por error o se usa reverse proxy público.

Recomendación:
Usar variable:
CORS_ORIGINS=https://181.212.166.187:8443,https://saas.tcdx.cl

Implementación sugerida:
const allowedOrigins = String(process.env.CORS_ORIGINS || '')
  .split(',')
  .map((origin) => origin.trim())
  .filter(Boolean);

app.use(cors({
  origin(origin, callback) {
    if (!origin) return callback(null, true);

    if (allowedOrigins.length === 0) {
      return callback(null, true);
    }

    if (allowedOrigins.includes(origin)) {
      return callback(null, true);
    }

    return callback(new Error('Origen no permitido por CORS'));
  },
  credentials: true,
}));

Criterios:
- En laboratorio puede quedar flexible.
- En producción privada, definir CORS_ORIGINS.
- No romper acceso del frontend.

17. PRIORIDAD ALTA PARA PRODUCCIÓN PRIVADA: FIREWALL / RED
=====================================================

Contexto:
El usuario indicó que producción real no estará expuesta a internet:
- Backend, AI Engine y BD estarán en red privada.
- Solo frontend accederá a backend.
- AI Engine y BD solo deberían ser alcanzables por backend o red interna autorizada.

Recomendación:
En AWS/OCI:
- DB sin IP pública.
- AI Engine sin IP pública.
- Backend sin IP pública si se usa reverse proxy/frontend privado.
- Security Group / NSG:
  - Frontend -> Backend: puerto 3000 o reverse proxy interno.
  - Backend -> DB: 5432.
  - Backend -> AI Engine: 8001.
  - Admin SSH solo desde IP/VPN autorizada.
- Bloquear 5432 y 8001 desde internet.
- Considerar VPN o bastion host.

Criterios:
- nmap desde fuera no debe ver DB ni AI Engine.
- Backend no debe aceptar tráfico desde orígenes no autorizados si no corresponde.
- Documentar matriz de red.
