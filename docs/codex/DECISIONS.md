# DECISIONS — TCDX ISO SaaS V4

Las siguientes decisiones provienen del Plan Maestro y se consideran `VERIFIED`.

| ADR | Estado | Decisión |
|---|---|---|
| ADR-001 | VERIFIED | No LLM direct SQL. El LLM recibe contextos autorizados. |
| ADR-002 | VERIFIED | PostgreSQL outbox first. Kafka sólo con necesidad/benchmark demostrado. |
| ADR-003 | VERIFIED | PostgreSQL pgvector first. Vector DB separada sólo con escala demostrada. |
| ADR-004 | VERIFIED | PostgreSQL graph abstraction first. Neo4j no es requisito inicial. |
| ADR-005 | VERIFIED | Extend Knowledge Base v2. No crear una segunda KB. |
| ADR-006 | VERIFIED | Extend Intelligence Engine. No crear un segundo orchestrator transversal. |
| ADR-007 | VERIFIED | Deterministic truth, AI explanation. Scores/gaps oficiales no los inventa el LLM. |
| ADR-008 | VERIFIED | Tenant learning via memory/RAG. No fine-tuning cross-tenant automático. |
| ADR-009 | VERIFIED | Authoritative regulatory sources. Web general no es Source of Truth legal. |
| ADR-010 | VERIFIED | `CODEX_VALIDATION_MODE = FOCUSED_MINIMAL`; CI/merge/deploy son manuales. |
| ADR-011 | VERIFIED | Temporalidad oficial de Math Governance debe ser contract-driven: `temporal_semantics` define campo canónico, significado, período, `as_of`, timezone y política de ausencia; `created_at`/`updated_at` no son fallback universal. |
| ADR-012 | VERIFIED | Status oficial de Math Governance debe ser contract-driven y domain-aware: `status_semantics` define dominio, mapping versionado, política de unknown visible y elegibilidad; no existe diccionario universal ni fallback silencioso a estados válidos. |
| ADR-013 | VERIFIED | Fallback legacy en Math Governance debe estar gobernado por el resolver: sólo `primary_absent` o `primary_no_rows` con contrato explícitamente autorizado pueden activar fallback; incompatibilidad, contrato inválido, filas excluidas, status/temporal/scale invalid no activan fallback. |
| ADR-014 | VERIFIED | Data Trust oficial de Math Governance es determinístico y versionado (`data-trust-model-v1`): consume señales PUI-01..PUI-06, separa confianza del valor de métrica, distingue insuficiencia de baja confianza y no usa IA. |
| ADR-015 | VERIFIED | El pipeline oficial único para fórmulas gobernadas es `officialCalculationOrchestrator -> sourceResolver -> source contracts/validation/Data Trust -> persisted calculation/snapshot`. `phase5_5_package3` no puede calcular ni persistir verdad paralela; sólo puede operar como capa de compatibilidad/proyección. |
| ADR-016 | VERIFIED | Los vocabularios legítimos producidos por dominios F5_5 deben reconciliarse contra `statusSemantics.service.js` mediante contratos por dominio y drift guard automatizado; `valid_to` futuro en `validity_interval` no es un evento futuro inválido, mientras que `event_stream`/`valid_from` futuro sigue excluido según contrato temporal. |
| ADR-017 | VERIFIED | El cierre residual HF3 mantiene semántica por productor: findings snapshot de readiness no tienen status operacional propio y usan `not_applicable` más temporalidad del snapshot padre; maturity acepta sólo vocabulario productor conocido; health components pueden validar con `started_at/completed_at` cuando `calculation_runs.period_start` es nulo. |
| ADR-018 | VERIFIED | Para `F5_5_SEVERITY_INDEX`, el source ownership publicado prevalece sobre `source_overrides`/`body.source_code`: `audit_findings_actions` es el source code canónico y `incident_operational_events/grc_incidents` no puede producir verdad paralela ni falso `SOURCE_SCHEMA_INCOMPATIBLE`; el override no canónico queda visible como warning/provenance. HF4 no generaliza esta política a fórmulas con overrides/indicadores legítimos ya existentes. |
| ADR-019 | VERIFIED | Para `F5_5_SEVERITY_INDEX`, el physical source canónico es `grc_readiness_findings` unido a `grc_readiness_snapshots`; el schema productor de snapshots tiene `generated_at`, `period_start` y `period_end`, pero no `source_as_of`. El contrato `audit_findings_actions` v9 y su adapter no pueden requerir ni fabricar `source_as_of`; una ausencia real de findings canónicos queda como dataset vacío/no calculable, no como portfolio de severidad en cero. |
| ADR-020 | VERIFIED | PUI-08 establece la matriz oficial computable como artefacto de cierre PRE-UI: las 53 fórmulas de `FORMULAS` se derivan de `FORMULA_SOURCE_MAP`, source contracts, consumers, dependencias, snapshot/lineage y escenarios empty/partial/sufficient/two-tenant. La matriz no es una lista manual ni habilita motores paralelos; consumers sólo pueden proyectar resultados oficiales persistidos o ejecutar el `officialCalculationOrchestrator`. |
| ADR-021 | VERIFIED | PUI-09 cierra formalmente la fase PUI y declara `PRE_UI_DATA_TRUTH_GATE=PASS` con evidencia runtime productiva post-PUI-08: no hay `calculated` con fuentes incompatibles/no disponibles, los calculated tienen snapshot, los datasets poblados tienen lineage, `not_calculable` no fabrica cero/completed, Data Trust v1 está presente y Severity Index conserva su fuente canónica. La siguiente fase autorizada es Fase 6 ampliada desde F6.8/6.8-01. |
| ADR-022 | VERIFIED | 6.8-01-HF1 corrige 6.8-01: el modelo canónico transversal de observaciones GRC ya existía en el Semantic Layer. `grc_observations` es el system of record canónico, `grc_observation_relations` es el modelo canónico de relaciones, `semanticLayer.service.js` es owner/runtime de persistencia, y `grcObservation.service.js` es fachada GRC. La observación canónica es append-only salvo supersession controlado, tenant-scoped, con `status_value`/`severity_value`, source snapshots/provenance/lineage y sin modelo paralelo. |
| ADR-023 | VERIFIED | 6.8-01-HF2 corrige el bootstrap runtime faltante de `grc.manual_observations`: el contrato semántico de observaciones manuales debe existir mediante forward migration registrada en `schema_migrations`, global (`tenant_id=NULL`), `published`, con v1 `published` y `current_version_id` apuntando a esa v1. Runtime closure post-deploy confirmó `SEMANTIC_CONTRACT_GRC_MANUAL_OBSERVATIONS=PASS_RUNTIME`, sin duplicados ni contratos tenant-specific. No se permite depender de re-ejecutar una migración histórica ni crear contratos tenant-specific con el mismo `source_code`. |
| ADR-024 | VERIFIED | 6.8-02 implementa PostgreSQL outbox para emisión gobernada de Observations sin modelo paralelo: `grc_observation_emission_outbox` almacena eventos tenant-scoped, idempotentes y reintentables; el productor inicial es `officialCalculationOrchestrator`; el consumer usa exclusivamente `semanticLayer.createManualObservation` para persistir en `grc_observations`. La regla inicial `official_calculation.data_trust_attention@1` sólo emite resultados `calculated` con Data Trust material (`TRUSTED_WITH_WARNINGS` o `LOW_CONFIDENCE`) y `observed_at` explícito; no-data, insufficient, source-incompatible, dependency-pending y fallas de fuente quedan no elegibles/ignored y no generan observaciones negativas. |
| ADR-025 | VERIFIED_LOCAL | 6.8-02-HF1 fija el contrato temporal del boundary Outbox -> Semantic Layer: las columnas `timestamptz` del outbox pueden llegar a Node.js como `Date`, pero `grcObservationEmitter.service.js` debe pasar `observed_at`, `period_start` y `period_end` a `semanticLayer.createManualObservation` como strings ISO-8601 UTC. `observed_at` requerido inválido/faltante no se reemplaza por `now()`; `period_start`/`period_end` pueden permanecer `null`; no hay migración, no hay cambios de fórmulas/source contracts y 6.8-02 runtime sigue pendiente de validación post-deploy. |

Una ADR `VERIFIED` sólo se revisa por evidencia objetiva, regresión, cambio aprobado de requisito, incompatibilidad demostrada o riesgo de seguridad.
