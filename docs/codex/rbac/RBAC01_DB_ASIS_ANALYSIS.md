# RBAC-01 DB AS-IS Analysis

Status: `COMPLETE_LOCAL`
Date: 2026-08-27
Evidence: `artifacts/rbac01-db-audit/*.csv`
Production DB modified: `NO`

## Scope

This analysis consumes the read-only DB audit artifacts already generated by the user. Codex did not reconnect to PostgreSQL and did not execute DB writes.

## Findings

- `roles.csv` contains 9 catalogued roles: `viewer`, `auditor`, `control_owner`, `compliance_manager`, `admin`, `tenant_admin`, `dealer`, `platform_admin`, `superadmin`.
- `users_by_role.csv` shows persisted users with `operativo`, but `operativo` is not catalogued consistently in `roles.csv`.
- `role_permissions.csv` shows `auditor` already has `dashboards.read`; the application-side role lists were the inconsistent layer for dashboard access.
- `admin` and `tenant_admin` are not privilege-equivalent: `admin` has `action.manage`, `audit.execute`, `control.manage`, `risk.manage`, `tenant.manage`; `tenant_admin` has `users.assign_roles`.
- `superadmin` and `platform_admin` are not privilege-equivalent: `superadmin` has `settings.manage` beyond the audited `platform_admin` set.
- `dealer_assignments.csv` confirms dealer access is assignment-scoped through active dealer-tenant relationships; dealer is not platform-wide.
- `tenant_modules.csv` contains active and inactive module states per tenant, including inactive advanced GRC/operational modules for ISO-like tenants.
- `entitlements.csv` separates technical capabilities, required permissions and commercial module keys.

## Conclusion

RBAC-01 must preserve raw effective roles during compatibility. The application can map a role to a canonical semantic family for navigation and coarse route grouping, but permission checks must continue to use the user's effective permissions and must not treat legacy role names as blind aliases.
